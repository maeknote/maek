## 확인된 원인

현재 `client/src/App.tsx:98`의 HTML 미리보기는 파일 내용을 `iframe.srcDoc`에 넣는다. 파일의 디렉터리 URL, 관련 자원 제공 경로, 전용 서버 연결 정보는 전달하지 않는다. `allow-scripts`는 이미 설정돼 있으므로 JavaScript 실행을 일괄 금지한 문제가 아니다.

조사한 실제 사례는 `/Users/yoonchul/life-os/000_Life_Areas/005_Routines/루틴 대쉬보드.html`이다.

1. `loadDefinition()`은 `api/definition`, `routine-workflow/routines.json` 순으로 요청한다(690행). 현재 미리보기에서는 이 상대경로가 원본 파일 폴더가 아닌 호스트 페이지 URL을 기준으로 해석된다.
2. `boot()`는 `api/health`로 쓰기 가능 여부를 확인하고, 정의와 기록을 읽는다(1360행 이후). 정의 읽기에 실패하면 오류 문구를 넣은 다음 `return`한다(1378행). 탭 전환, 주간 이동, 편집, 다운로드 등의 이벤트 등록은 그 뒤에 있어 실행되지 않는다.
3. `routine-workflow/serve.py`가 전용 API를 구현한다. 정의 읽기에는 `X-Routines-Version`, 정의 저장에는 `X-Routines-Base-Version`을 사용하며, `/api/log/toggle`로 기록을 변경한다. HTML을 표시하는 것만으로 이 서버가 실행되거나 연결되지는 않는다.
4. 같이 있는 `루틴 대쉬보드 열기.command`는 기본 포트 8796에서 서버 상태를 확인하고, 필요하면 Python 서버를 실행한 뒤 해당 서버의 HTML URL을 연다. 현재 앱에는 이 실행 환경을 연결하는 기능이 없다.
5. `server/host.ts:182`의 raw 경로는 이미지와 PDF만 제공한다. 현재 구조에는 HTML 옆의 JS/CSS/JSON을 원래 디렉터리 구조로 제공하는 경로가 없다. 운영 서버의 SPA fallback은 없는 파일 요청에 앱 HTML을 반환할 수도 있어 JSON 파싱 오류로 나타날 수 있다.
6. 현재 sandbox에는 `allow-downloads`가 없다. 데이터 연결을 고친 뒤에도 루틴 대시보드의 JSON 다운로드를 별도로 검증해야 한다. 클립보드 기능도 실제 브라우저 권한 정책에 맞춰 확인해야 한다.

## 검증 근거와 한계

- Fastify `inject`로 현재 호스트의 `/api/health`, `/api/definition`, `/api/log`, `/routine-workflow/routines.json` 요청이 모두 404임을 확인했다. 운영 SPA fallback은 이 검사에 포함하지 않았다.
- 실제 HTML의 inline script를 Node VM에서 실행하고 fetch 실패를 주입했다. 결과는 `읽기 전용`, `불러오지 못했다: 정의를 불러오지 못했다`, 등록된 이벤트 리스너 0개였다. 이는 초기화 중단 경로의 재현이며 실제 브라우저 네트워크 캡처는 아니다.
- 기존 E2E의 HTML fixture는 `<h1>Rendered HTML</h1>`뿐이며 iframe 표시 여부만 검사한다(`tests/e2e/workspace.spec.ts:24,132`). 상호작용과 데이터 연동 실패를 잡을 수 없다.
- 이번 조사에서는 사용자 대시보드 서버를 실행하거나 실제 루틴 파일에 쓰기 요청을 보내지 않았다.

## 구현 순서

### 1. 실패가 드러나는 회귀 시나리오부터 추가

임시 workspace에 독립적인 검증 fixture를 만든다. 실제 사용자 파일은 테스트에서 수정하지 않는다.

- inline JavaScript 버튼: 클릭 전후 DOM 변화.
- 중첩 폴더 HTML: 인접 JS/CSS, JSON, 이미지 로딩과 하위 페이지 이동.
- 작은 테스트 API 서버: health, 데이터 읽기, 변경, 재조회.
- 서버 중단, 없는 파일, 잘못된 JSON, 저장 충돌, API 오류.

기존 미리보기로 어떤 테스트가 실패하는지 확보한다. 루틴 대시보드의 실제 스크립트와 익명화된 최소 데이터로 초기화 회귀도 검사한다.

### 2. 파일 기반 HTML에 디렉터리 URL 제공

`App.tsx`의 HTML 분기를 전용 `HtmlArtifactPreview` 컴포넌트로 분리한다. HTML을 전용 URL로 제공하고 iframe의 `src`로 로드하여 상대경로 해석에 원본 디렉터리를 반영한다.

- 전용 artifact 파일 서버는 선택한 workspace 내부의 허용된 파일만 제공한다. HTML/JS/CSS/JSON/이미지에 맞는 MIME을 사용한다.
- 없는 자원은 실제 404를 반환한다. 앱의 `index.html`로 대체하지 않는다.
- 한글, 공백, 중첩 폴더, query/hash, workspace 안에서의 부모 디렉터리 참조를 검증한다. 정규화 후 workspace 밖으로 나가는 경로 및 symlink 우회는 차단한다.
- 실행 가능한 HTML은 편집기와 다른 origin에서 제공한다. 포트 분리 등을 사용하고, 기존 편집기 API나 부모 DOM에 대한 접근을 열지 않는다. 기존 raw 경로의 허용 목록을 단순히 확장하지 않는다.
- workspace 전환, 파일 이동, 서버 재시작 시 오래된 URL이 다른 workspace를 가리키지 않게 한다.

완료 기준: HTML과 주변 파일만으로 구성된 아티팩트가 클릭·데이터 읽기·탐색을 수행한다. 이 단계에서는 전용 backend가 필요한 저장 기능까지 해결된 것으로 보지 않는다.

### 3. 루틴처럼 서버가 필요한 아티팩트 연결

파일 미리보기와 연결할 로컬 앱 URL을 artifact별로 지정하는 모델을 추가한다. 루틴은 기존 `serve.py`가 제공하는 실제 HTML URL을 iframe에서 열어 HTML과 API가 같은 서버를 사용하게 한다. 루틴 전용 API를 oh-my-maek의 `/api` 아래에 복제하지 않는다.

- 설정은 workspace와 artifact 상대경로를 키로 관리하고 UI 세션 메타데이터와 분리한다.
- 최초 버전은 실행 중인 로컬 서버 연결, health 확인, 연결 실패 안내, 다시 연결, 외부 브라우저 열기를 제공한다.
- 연결 URL은 loopback 주소로 제한하고 origin과 대상 경로를 표시한다. 포트만 맞는 다른 서비스가 연결되지 않도록 기대한 서비스 응답을 확인한다. 루틴 health 응답의 식별 정보가 부족하면 최소 응답 구조 검사와 명시적으로 지정한 URL을 사용하고, 서비스 식별 필드 추가를 후속 개선으로 둔다.
- 전용 서버 자동 실행은 후속 단계로 둔다. 명시적으로 등록된 실행 명령/cwd, 프로세스 소유권, 중복 실행 방지, 종료와 로그 처리 규칙을 갖춘 뒤 제공한다. HTML 내용이나 파일명만 보고 임의 명령을 실행하지 않는다.
- 루틴의 기존 버전 확인·백업·기록 수정 동작은 기존 서버가 담당하도록 유지한다.

완료 기준: 임시 루틴 데이터 복사본에서 정의/기록 표시, 주간 이동, 탭 전환, 정의 저장, 기록 토글, 새로고침 후 영속성이 확인된다. 외부 수정 뒤 저장 충돌도 기존 정책대로 처리된다.

### 4. 실패 상태와 iframe 기능 정리

- 도구 모음에 현재 모드(파일 미리보기/로컬 앱), 연결 상태, 새로고침, 외부 열기를 제공한다.
- 파일 제공 실패와 서비스 연결 실패는 앱이 직접 설명한다. 단순 iframe `load` 이벤트만으로 내부 초기화 성공을 판정하지 않는다.
- 파일 기반 런타임에는 JS 오류와 Promise rejection을 전달하는 진단 채널을 검토한다. 메시지의 iframe source와 세션을 검증한다. 별도 서버 앱은 협력 코드 없이 내부 오류 전체를 수집할 수 없으므로 health 상태와 내부 실행 상태를 구분한다.
- 필요한 다운로드 및 클립보드 동작을 검증하고 최소 권한을 적용한다. 현재처럼 같은 origin에서 scripts와 same-origin을 동시에 허용하는 구조를 격리 경계로 간주하지 않는다.
- 루틴 자체의 초기화도 별도 개선 대상으로 삼는다. 탭 등 데이터와 무관한 이벤트는 먼저 등록하고, 데이터 로딩 실패 시 재시도와 구체적 오류를 표시한다. 데이터가 필요한 편집/저장은 비활성화한다. 이 변경은 life-os 파일 수정 범위이므로 앱 런타임 구현과 분리한다.
- 탭 전환이나 외부 변경으로 iframe이 재생성될 때 미저장 폼이 사라지는지 검증한다. 저장 상태를 알 수 없는 앱을 자동으로 강제 새로고침하지 않는다.

## 최종 수용 기준

1. 단일 HTML 버튼 및 주변 파일을 읽는 HTML이 모두 작동한다.
2. 루틴 전용 서버에 연결하면 화면 표시부터 저장·재조회까지 작동한다.
3. 서버가 없거나 데이터가 깨졌을 때 실패 이유와 다음 행동이 표시된다.
4. 다운로드·클립보드·탭 전환 동작이 실제 브라우저에서 검증된다.
5. artifact에서 workspace 외부 파일이나 편집기 DOM/API에 접근할 수 없다.
6. 개발 모드와 빌드 후 실행 모두에서 테스트하며 기존 Markdown 편집·충돌 보호·파일 미리보기가 유지된다.

권장 작업 묶음은 (1) 회귀 테스트와 파일 기반 런타임, (2) 로컬 서비스 연결과 루틴 저장 검증, (3) 진단 UX 및 실행 관리다. 사용자 관점의 완료는 iframe 표시가 아니라 실제 데이터 조회와 버튼 실행, 저장 후 재조회로 판단한다.
