# life-os 리소스 사용 조사 — 2026-10-06

조사 환경: macOS, 개발 모드 Maek(Vite :3000 / Local Core :3001),
`/Users/yoonchul/life-os`. 측정 시각은 약 10:29–10:38 KST.
외부 연구 작업이 계속 진행 중이므로 파일 수는 측정 시점마다 달라질 수 있다.
아래 조사 수치와 소스 위치는 수정 전 기준이다. 조사 당시에는 앱 코드와 life-os
원본을 변경하지 않았다. 이후 구현 내용은 문서 끝에 기록한다.

## 판단

정상적인 연구 데이터 생성이 부하의 계기이고, Maek의 이벤트 처리와 데이터베이스
검색 구조가 이를 증폭시키는 것이 가장 유력하다. 약 1만 개의 사용자 파일을
다루는 작업공간 자체를 비정상으로 볼 근거는 없다. 악성 활동이나 무한 변경
루프를 입증한 것도 아니다.

확인한 구조적 결함은 다음과 같다.

1. 일반 파일 추가·삭제마다 데이터베이스 목록 전체를 다시 요청한다.
2. 데이터베이스 검색은 탐색기에서 제외하는 Python 가상환경까지 재귀 순회한다.
3. 파일 추가마다 전체 노드 배열을 복사·정렬하고 탐색 트리를 재구성한다.

이 경로는 실제 코드의 이벤트 핸들러 재현 및 읽기 전용 벤치마크로 확인했다.
Chrome 탭의 성능 추적은 연결 부재로 수행하지 못했으므로, 경고를 발생시킨
정확한 브라우저 CPU·힙 점유율과 메모리 누수 여부는 미확정이다.

## 주원인: 일반 파일 이벤트가 전체 DB 검색으로 이어짐

`client/src/features/workspace/model/workspaceStore.ts:1364`는 각 파일 변경을
`maek:workspace-change`로 전달한다.
`client/src/features/explorer/Explorer.tsx:467`의 `refresh()`는 직접
`/api/databases`를 호출하고, 482–488행은 일반 `add`/`unlink`까지 이 호출의
조건으로 사용한다. Debounce, 실행 중 요청 공유, 후속 요청 합치기가 없다.
이 경로는 TanStack Query의 요청 중복 제거를 거치지 않는다.

해당 소스의 이벤트 핸들러를 TypeScript로 변환하고 `refresh`만 카운터로 대체한
독립 실행에서 이미지 추가 1,000건은 DB 검색 호출 1,000건을 만들었다.
이미지 내용 변경 1,000건은 0건이었다. 따라서 모든 저장이 아니라 특히 대량
추가·삭제가 이 문제를 촉발한다.

`server/features/database/service.ts:317`의 `listDatabases()`는 매 요청마다
`find()`로 루트를 다시 순회한다. 279행의 별도 제외 목록에는 `.venv`,
`site-packages`, `__pycache__` 등이 없다. 이는
`server/workspace/filesystem.ts`의 탐색기·감시 제외 규칙과 다르다.

같은 life-os에서 검색 순회만 재현한 Node 벤치마크 결과:

| 순회 정책 | 디렉터리 | 읽은 엔트리 | 발견 DB | 소요 |
| --- | ---: | ---: | ---: | ---: |
| 현재 DB 검색 규칙 | 9,351 | 105,991 | 6 | 328ms |
| 탐색기 제외 이름을 적용한 비교 | 908 | 10,900 | 6 | 35ms |

현재 검색 범위의 `.venv`에는 디렉터리 8,318개와 파일 85,613개가 있었다.
DB 검색에서 불필요한 영역을 읽어 단일 순회 비용이 약 9.4배 증가했다.
비교는 읽기 전용 순회이며, 실제 API의 SQLite·manifest 처리와 동시 요청 비용은
포함하지 않는다. 같은 DB 6개를 찾았다는 것도 현재 life-os에 대한 결과이다.

실행 중 서버의 3초 `sample`에는 libuv 작업 스레드의 `scandir`, `readdir`,
디렉터리 `open`이 반복해서 나타났다. 이벤트가 26초에 2건인 구간에도 서버 CPU가
높고 여러 HTTP 연결이 유지되었다. 앞선 대량 추가로 생성된 DB 검색 요청이
계속 처리되는 설명과 일치한다. 실제 누적 요청 수와 각 연결의 URL은 계측하지
않았으므로, 요청 적체 규모는 추정이며 무한 루프라고 단정하지 않는다.

## 브라우저 측 증폭: 파일 한 건마다 전체 트리 갱신

`workspaceStore.ts:1433` 부근은 노드 추가마다 기존 배열을 `filter`로 읽고,
새 배열을 만들고, 전체를 정렬한다. `Explorer.tsx:502`는 바뀐 배열로 전체
트리를 재구성한다. DB 검색 응답도 매번 새 `databases` 배열을 설정하므로
`databaseNames`와 트리 계산을 다시 수행한다.

실제 파일 9,844개의 이름으로 같은 배열 처리 알고리즘을 재현하고 이미지
1,000건을 추가했을 때 반복 처리에 1,187ms가 걸렸다. 같은 추가를 모아서
Map에 반영하고 한 번 정렬하면 2ms였다. 이는 Node에서 수행한 배열 연산 비교로,
브라우저 렌더링·React·react-arborist 비용은 제외한다. 앱 전체가 이 비율로
빨라진다는 뜻은 아니다.

`AppShell.tsx:65`와 `Explorer.tsx:275`는 전체 Zustand 상태를 구독한다.
관계없는 로그 변경도 전역 상태 갱신을 일으키므로 구독 범위를 좁힐 여지가 있다.
트리의 화면 행 가상화는 전체 데이터 구성 비용까지 없애주지 않는다.

## 수정 우선순위와 검증 조건

1. **DB 목록 갱신 조건 축소 및 요청 공유:** 일반 이미지·데이터 파일의 추가와
   삭제는 DB 등록 목록을 다시 읽지 않게 한다. Manifest와 관련 디렉터리 변화는
   모아서 갱신하고 Explorer와 DatabaseView가 같은 조회를 공유한다.
2. **서버 DB 발견 인덱스와 제외 규칙 정리:** 초기 발견 이후 manifest·디렉터리
   변화로 인덱스를 갱신한다. `.venv` 등 공통 제외 정책을 적용하고, 사용자
   문서 폴더를 부하 회피 목적으로 임의 제외하지 않는다.
3. **트리 변경 배치 처리:** 이벤트 묶음마다 노드를 한 번 갱신·정렬한다.
   관계없는 파일 내용 변경으로 트리 상태를 새로 설정하지 않고, UI 구독을
   필요한 상태로 제한한다. 대량 변경 중에도 연속적으로 진행 상황을 반영해야
   하므로 단순한 무기한 debounce는 피한다.
4. **미리보기 활동 제어:** 비활성 HTML의 polling을 중지하거나 활성 상태를
   전달한다. 이후 watcher 회수와 큰 workspace의 점진적 트리 로딩을 검토한다.

수정 후에는 임시 workspace에 이미지 1,000개 이상을 추가하는 동안 DB 목록
요청 수가 파일 수에 비례하지 않는지, 가상환경 내부가 검색되지 않는지,
최종 트리가 정확한지, DB manifest 생성·이동·삭제가 정상 반영되는지 확인한다.
Chrome 연결이 가능할 때 같은 작업으로 탭의 CPU·힙·장시간 작업을 측정해
실제 경고가 해소되는지도 검증해야 한다.

## 후속 구현 — 단계별 변경

근본 원인은 파일 하나의 변경을 너무 넓은 갱신으로 연결하는 데 있다. DB 검색은
그 영향 범위에 포함된 비용 큰 작업이었다. 이에 다음 단계를 각각 개선했다.

| 단계 | 구현 |
| --- | --- |
| 발견·감시 범위 | DB 발견도 탐색기·watcher와 같은 제외 정책 및 파일 인덱스를 사용 |
| 이벤트 전달 | 50ms/512건의 순서 보존 배치, 내용 변경 중복 합치기, 느린 SSE 연결의 버퍼 제한 |
| 영향 범위 판정 | 트리 구조·DB 등록 목록·해당 DB 행·열린 파일 내용을 각각 갱신 |
| 데이터 조회 | 최초/복구 스캔 공유, 이후 경로 증분 반영, 등록 목록과 행의 Query 캐시 공유 |
| 화면 반영 | 묶음당 한 번 정렬, 바뀌지 않은 노드·가지 참조 보존, Zustand 구독 범위 축소, 파일 선택창 가상화 |
| 자원 수명 | 복원 미리보기 지연 생성, 비활성 HTML 반복 callback 제어, 미사용 runtime 60초 후 회수 |

일반 파일 추가·삭제가 더 이상 DB 등록 목록 갱신으로 이어지지 않는다. Manifest 생성·
수정·삭제와 등록된 폴더 이동은 계속 반영한다. 외부에서 manifest를 지운 뒤 SQLite의
파생 캐시가 manifest를 다시 만들지 않도록 기존 SQLite-only 등록 목록의 이관은 한 번만
실행한다. 사용자 문서나 데이터셋 폴더를 성능 회피 목적으로 제외하지 않았다.

전체 스캔은 최초 발견, watcher 복구, 명시적인 구조 변경 API 직후의 정합성 확인에
남아 있다. 일반 외부 이벤트마다 다시 순회하지 않는다. 복잡한 범용 의존성 시스템이나
앱별 예외 대신 workspace의 경로 인덱스와 각 기능의 작은 영향 판정 함수로 구현했다.

HTML은 비활성 상태에서 함수형 `setInterval` callback을 건너뛰되 예약된 저장용
`setTimeout`을 유지한다. RAF·재귀 timeout·WebSocket은 활동 이벤트로 페이지가
조절할 수 있다. 모든 종류의 JavaScript 작업을 자동 정지시키는 기능은 아니다.

- 기존 생성 파일 9,000개에 1,000개를 추가한 시험에서도 세 조회는 각각 0건이었다.
  추가 파일 검색과 편집 완료까지 3,125ms가 걸렸다. 이 시험에서 검색어 없는 파일
  선택창이 전체 1만 행을 렌더링하는 추가 병목을 발견해 화면 주변 행만 렌더링하도록
  보완했다. 검색 결과를 잘라내지 않고 전체 스크롤 및 키보드 접근을 유지한다.
- 비활성 HTML의 반복 callback은 멈추고 일회성 timeout은 완료됐다. 탭 재선택 시
  수정된 DOM 상태와 반복 실행이 복원됐으며, reload 후 비활성 iframe은 지연 생성됐다.

더 넓은 추가 실행(`database-parity`, `note-state`, `workspace`, 새 부하 테스트)은
47개 중 30개 통과, 17개 실패였다. 실패 16개는 수정 전 HEAD `576bad3`의 임시 복사본과
별도 포트에서도 같은 원인으로 재현했다. 고정된 2026년 9월 날짜 기대, 기존 세션/탭
검증, 달라진 메뉴·입력 선택자, 파일 열기 경합 등이 포함된다. 나머지 1개는 테스트가
임시 폴더를 삭제하는 중 `ENOTEMPTY`가 발생한 사례로, 수정 전 실행과 변경 후 단독
3회 실행에서는 모두 통과했다. 전체 E2E suite가 통과했다고 볼 수는 없다.

CPU·힙과 경고 재발 여부는 연결 부재로 측정하지 못했다. 위 시험은 별도 Chromium과
임시 workspace에서 수행한 결과이며 실제 Chrome 경고 해소를 확인한 결과는 아니다.
