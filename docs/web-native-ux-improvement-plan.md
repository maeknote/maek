# Maek 웹 네이티브 UI/UX 개선 분석

## 1. 문서 목적

Maek 웹 버전은 macOS 앱의 Markdown 편집 기능과 파일 탐색 구조를 브라우저로 옮긴 제품이다. 현재 구현은 로컬 파일을 안전하게 편집하고 기존 앱의 기능을 재현하는 데 강점이 있지만, 주소·방문 기록·새 탭·반응형 레이아웃처럼 브라우저가 기본으로 제공하는 사용 모델을 충분히 활용하지 못한다.

이 문서는 현재 코드에서 확인한 구조를 바탕으로 다음 목표를 위한 개선 방향을 정리한다.

- 브라우저의 탐색 모델과 Maek 내부 탐색을 일치시킨다.
- 이미 구현된 기능을 사용자가 자연스럽게 발견하고 연결해서 쓰게 한다.
- 로컬 폴더와 Markdown 파일이라는 Maek의 정체성을 유지한다.
- 좁은 창, 키보드, 여러 브라우저 탭에서도 주요 작업을 안정적으로 수행하게 한다.

이 문서의 구현 관련 서술은 분석 당시 작업 트리를 기준으로 한다. 실제 화면의 시각적 완성도와 브라우저별 단축키 동작은 별도 검증이 필요하다.

## 2. 제품 방향

Maek 웹 버전의 권장 제품 정의는 다음과 같다.

> 로컬 폴더를 탐색하고, 문서를 읽고 쓰며, 같은 자료를 목록·보드·미리보기 등 여러 방식으로 다루는 웹 워크스페이스.

웹 전환의 목적은 데스크톱 앱과 같은 창을 브라우저 안에 재현하는 데 있지 않다. 사용자가 문서마다 주소를 갖고, 링크로 이동하고, 뒤로 가기로 맥락을 되찾으며, 여러 탭에서 자료를 비교하는 경험을 제공해야 한다.

기능 확장도 이 원칙을 따라야 한다. 새로운 독립 기능을 늘리는 것보다 이미 있는 파일 탐색, 최근 문서, Markdown 속성, 칸반, 미리보기를 하나의 작업 흐름으로 연결하는 것이 우선이다.

## 3. 현재 구조에서 확인된 강점

현재 구현에는 웹 네이티브 경험으로 발전시키기 좋은 기반이 이미 있다.

- 실제 폴더와 파일 이름을 유지하며 Markdown을 원래 위치에서 편집한다.
- 자동 저장, 외부 파일 변경 감지, 충돌 보호, 사본 저장 흐름이 있다.
- 브라우저 세션별 열린 탭과 최근 파일을 저장한다.
- 빠른 파일 검색, 내부 노트 링크, 이미지 삽입, 표·수식·코드·체크리스트를 지원한다.
- 이미지·PDF·텍스트·HTML 아티팩트 미리보기를 제공한다.
- 폴더의 Markdown 속성을 이용한 칸반 보기가 있다.
- 최근 문서와 열린 문서를 보여주는 워크스페이스 대시보드가 있다.
- 라이트·다크 테마와 중앙 디자인 토큰이 존재한다.

따라서 전면 재작성보다 탐색 모델과 정보 구조를 교정하고, 끊긴 기능 연결을 복구하는 접근이 적합하다.

## 4. 핵심 문제

### 4.1 내부 상태와 브라우저 탐색이 분리되어 있다

현재 문서 열기와 전환은 `openFile`, `setActiveTab` 등 앱 내부 상태로 처리된다. 문서와 폴더의 상태가 URL 및 브라우저 방문 기록과 연결되는 구현은 확인되지 않았다.

이 구조에서는 다음 문제가 생긴다.

- 주소를 복사해 같은 문서로 돌아오기 어렵다.
- 뒤로/앞으로 버튼이 Maek 내부의 문서 이동을 반영하지 않는다.
- 새 브라우저 탭이나 창에서 특정 문서를 바로 열기 어렵다.
- 새로고침이나 복원 시 사용자가 기대하는 화면과 앱의 세션 상태가 충돌할 수 있다.
- 검색 결과에서 문서를 확인한 뒤 원래 검색 맥락으로 돌아가기 어렵다.

### 4.2 내부 탭이 폴더 탐색 공간과 경쟁한다

Explorer는 검색, 워크스페이스 선택, 열린 노트, 폴더 트리를 한 패널에 배치한다. 열린 노트가 늘어나면 폴더 탐색 영역이 줄어든다. 브라우저 자체에도 탭이 있기 때문에 내부 탭의 역할이 명확하지 않으면 사용자는 두 종류의 탭을 동시에 관리해야 한다.

### 4.3 주요 기능의 진입점이 숨겨져 있다

폴더 칸반은 폴더의 우클릭 메뉴를 통해 열린다. 이 기능을 모르는 사용자는 존재 자체를 발견하기 어렵다.

Markdown frontmatter를 속성 형태로 편집하는 `FrontmatterPanel`과 `PropertiesView` 컴포넌트도 존재하지만, 현재 기본 편집 화면에서 연결되어 렌더링되는 흐름은 확인되지 않았다. 칸반이 사용하는 `status`를 문서에서 직접 보고 수정하는 경험이 끊겨 있다.

### 4.4 대시보드가 재진입 작업보다 상태 요약에 가깝다

현재 대시보드는 열린 탭 수, 최근 파일 수, 테마 등 제품 상태를 요약한다. 재방문 사용자가 실제로 원하는 것은 이어 쓰던 문서, 최근 작업한 폴더, 고정한 문서처럼 즉시 다음 행동으로 이어지는 정보일 가능성이 높다.

### 4.5 검색이 빠른 파일 열기에 한정된다

현재 검색은 파일명과 경로를 기준으로 문서를 빠르게 여는 기능이다. 이 기능은 유용하지만 본문 검색과는 다르다. 검색 결과가 독립 화면이 아니므로 여러 문서를 비교할 때 검색을 반복할 가능성이 있다.

### 4.6 브라우저 기본 단축키와 충돌한다

`Cmd/Ctrl+P`, `O`, `N`, `W`는 브라우저에서도 인쇄, 파일 열기, 새 창, 탭 닫기 등에 사용한다. 앱에서 `preventDefault()`를 사용해도 브라우저나 운영체제가 먼저 처리하는 조합은 일관되게 제어되지 않을 수 있다.

### 4.7 데스크톱 창을 전제로 한 고정 크기와 장식이 남아 있다

파일 검색창과 워크스페이스 선택 패널은 고정 폭 중심이며, 큰 화면의 본문 폭도 제한되지 않는다. 상시 사이드바에 유리 효과와 둥근 패널을 적용한 구조는 데스크톱 앱의 창 형태를 강조하지만, 브라우저의 다양한 창 폭에서는 정보 밀도와 읽기 폭을 조절하기 어렵다.

## 5. 권장 정보 구조

### 5.1 전역 구조

```text
Maek
├── 홈
│   ├── 이어 쓰기
│   ├── 최근 문서
│   ├── 최근 폴더
│   └── 고정한 문서
├── 검색
│   ├── 빠른 파일 열기
│   └── 본문 검색 및 필터
├── 폴더
│   ├── 목록 보기
│   └── 보드 보기
├── 문서
│   ├── 읽기/편집
│   ├── 속성
│   ├── 미리보기
│   └── 관련 문서 이동
└── 설정
    ├── 워크스페이스
    ├── 외관
    └── 서버 제어
```

### 5.2 사이드바

사이드바는 다음 순서로 구성하는 것이 좋다.

1. 워크스페이스 선택기
2. 항상 보이는 검색 진입점
3. 새 노트 버튼
4. 홈·최근·즐겨찾기
5. 폴더 트리
6. 접을 수 있는 열린 문서 목록
7. 설정

폴더 트리는 Maek의 로컬 파일 기반 정체성이므로 중심 탐색으로 유지한다. 열린 문서 목록은 반복 전환을 돕는 보조 영역으로 취급한다. 내부 탭과 브라우저 탭은 다음 역할로 구분한다.

- 브라우저 탭: 독립 작업, 문서 비교, 다른 작업 맥락 유지
- Maek 열린 문서: 같은 작업 맥락 안에서 빠른 전환과 미저장 상태 확인

내부 탭을 제거할 필요는 없지만, 실제 사용 관찰 전까지 제품의 주 탐색 모델로 두지 않는 것이 좋다.

### 5.3 문서 상단

브라우저에서는 탭 바와 주소창이 이미 세로 공간을 차지한다. 따라서 문서 상단에 앱 버전과 같은 다층 크롬을 다시 만들지 않는다. 폴더 경로도 문서마다 반복하지 않는다. 권장 구조는 **본문에 포함된 제목과 문서 작업**, **요청할 때만 펼치는 속성**이다. 평상시 고정 문서 헤더는 없다.

권장 데스크톱 구조는 다음과 같다.

```text
  [사이드바]
  Browser-native workspace                         [속성] [•••]        ← 본문
  문서 내용이 바로 이어짐
```

### 폴더 위치는 열린 탭에서 다룬다

- 열린 탭에서 우클릭하면 `폴더에서 보기`를 제공한다.
- 같은 메뉴에서 `Finder에서 보기`, `상대 경로 복사`, `문서 링크 복사`, `탭 닫기`를 제공한다.
- 이름이 같은 문서가 여러 개 열렸을 때만 탭 보조 텍스트로 부모 폴더명을 표시한다.
- 현재 위치를 항상 보여주는 breadcrumb는 만들지 않는다.

### 문서 화면에 남는 것

문서 화면에는 다음만 남긴다.

- 사이드바가 접혀 있을 때만 나타나는 `사이드바 열기`
- 본문 첫 요소인 편집 가능한 문서 제목
- 제목 오른쪽의 `속성`과 `•••` 문서 메뉴
- 미저장 상태를 표시하는 Open Tabs 항목의 점
- 충돌과 연결 오류처럼 해결이 필요한 경우에만 나타나는 문서 경고

`문서 링크 복사`는 열린 탭의 우클릭 메뉴와 문서 `•••` 메뉴 양쪽에서 접근할 수 있다. 별도의 상시 링크 아이콘은 두지 않는다.

저장 상태는 메시지를 계속 점유하지 않도록 상태별로 다르게 표현한다.

| 상태 | 표시 | 동작 |
|---|---|---|
| 변경 없음 | 숨김 | 상단을 조용하게 유지 |
| 로컬 변경 | 열린 탭의 작은 점 | 문서 면적을 쓰지 않고 미저장 상태를 알림 |
| 저장 중 | Open Tabs 항목의 점 유지 | 자동 저장이 끝날 때까지 미저장 상태를 유지 |
| 저장 완료 | Open Tabs 항목의 점 제거 | 별도의 성공 메시지 없이 본문 공간을 유지 |
| 충돌 | 빨간색 `Conflict` 버튼 | 클릭하면 해결 패널을 열고 본문 상단에도 상세 배너 표시 |
| 오프라인·서버 오류 | `Disconnected` 버튼 | 재연결 상태와 저장되지 않은 변경을 설명 |

### 제목은 헤더가 아니라 문서의 첫 부분이다

- 제목은 현재처럼 편집할 수 있지만 고정 헤더 밖, 문서 스크롤 영역의 첫 요소로 둔다.
- 클릭하거나 키보드로 포커스하면 입력 상태가 드러난다. Enter 또는 blur로 확정하고 Escape로 취소한다.
- 파일 확장자 `.md`는 제목에서 숨기되 문서 메뉴나 경로 툴팁에서 실제 파일명을 확인할 수 있게 한다.
- 이름을 바꾸는 동안에는 저장 상태와 구분되는 진행 표시를 사용한다.
- 제목은 문서 시작점에서 충분히 크게 보이고 아래로 스크롤하면 자연스럽게 사라진다.
- `문서 내용 복사` 아이콘은 제목 옆에 상시 두지 않는다. 의미가 모호하고 제목의 시각적 중심을 흔들기 때문에 문서 메뉴로 이동한다.

### 속성은 상시 세 번째 줄로 만들지 않는다

- 제목 오른쪽의 `속성` 버튼을 누르면 popover 또는 제목 아래의 임시 패널을 연다.
- 사용자가 `status`를 자주 바꾸는 것이 확인되면 제목 아래에 값 하나를 표시할 수 있다. 기본 설계에는 넣지 않는다.
- 태그와 날짜를 항상 칩으로 나열하지 않는다. 전체 YAML/속성 편집기는 필요할 때만 연다.
- YAML 오류가 있으면 속성 버튼을 `속성 오류` 상태로 바꾸고 원문 편집기로 바로 이동시킨다.
- 속성이 전혀 없어도 제목 옆의 `속성` 버튼은 유지한다. 버튼의 툴팁과 빈 패널에서 속성 추가 기능을 안내한다.

속성 패널은 기본적으로 본문 높이를 밀어내지 않는 popover가 적합하다. 여러 속성을 길게 편집하거나 YAML 원문을 열 때만 제목 아래에 인라인 패널로 전환한다. 닫으면 즉시 원래 본문 면적을 회복한다.

### 문서 상단의 작업 구분

비슷해 보이는 복사 기능은 다음처럼 구분한다.

| 작업 | 위치 | 사용자에게 보이는 이름 | 결과 |
|---|---|---|---|
| 문서 주소 복사 | 열린 탭 우클릭 또는 `•••` 메뉴 | `문서 링크 복사` | 현재 컴퓨터의 Maek에서 이 문서를 여는 URL |
| Markdown 복사 | `•••` 문서 메뉴 | `Markdown 내용 복사` | frontmatter를 포함한 전체 파일 내용 |
| 표시 텍스트 복사 | 본문 선택 메뉴 | 브라우저 기본 `복사` | 사용자가 선택한 텍스트 |
| 파일 경로 복사 | `•••` 문서 메뉴 | `상대 경로 복사` | 워크스페이스 기준 파일 경로 |

문서 링크를 복사하면 `이 컴퓨터의 Maek 링크를 복사했습니다`라는 토스트를 보여 외부 공유 링크와 혼동하지 않게 한다.

### 읽기/편집 모드

읽기/편집 전환은 모든 사용자에게 필요한 기능으로 확인되기 전까지 상단의 상시 토글로 두지 않는다. 기본은 지금과 같은 즉시 편집 상태로 유지한다. 읽기 모드를 도입한다면 `•••` 메뉴와 명령 팔레트에서 먼저 제공하고, 사용 빈도가 확인되면 제목 옆의 1차 작업으로 올린다.

읽기 모드에서는 제목과 속성의 실수 편집을 막고 본문 링크, 선택, 인쇄에 집중한다. 편집 모드에서는 제목·속성·본문을 수정할 수 있다. 모드 자체는 URL query가 아니라 브라우저 탭의 UI 상태로 저장하는 편이 자연스럽다.

### 스크롤 동작

정상 상태에서는 문서 상단에 고정되는 요소가 없다.

1. 문서 시작점에서 제목, 속성 버튼, 문서 메뉴와 본문을 보여준다.
2. 아래로 스크롤하면 제목과 작업 버튼은 본문과 함께 사라진다.
3. 현재 문서명은 브라우저 탭 제목과 Maek의 열린 탭에서 확인한다.
4. 저장이 완료되면 Open Tabs 항목의 점이 사라진다.
5. 충돌과 연결 오류는 해결될 때까지 본문 위에 고정된 경고로 남는다.

이 방식은 긴 문서를 읽을 때 Maek 자체의 고정 크롬을 없앤다. 문서 메뉴가 필요하면 문서 시작점으로 돌아가거나 열린 탭의 우클릭 메뉴를 사용한다.

### 좁은 창 구조

폭이 좁을 때는 정보를 억지로 한 줄에 유지하지 않는다.

```text
[☰]
Browser-native workspace  [•••]
문서 본문
```

- 경로는 표시하지 않는다.
- 문서 링크 복사와 속성은 `•••` 메뉴 안으로 이동한다.
- 제목은 본문 안에 유지하되 크기와 좌우 여백을 한 단계 줄인다.
- 충돌이나 연결 오류는 아이콘만 남기지 않고 짧은 텍스트를 유지한다.

### 상호작용 우선순위

문서 상단에 둘 수 있는 작업은 다음 기준으로 승격하거나 메뉴로 내린다.

1. 거의 모든 문서에서 반복되는가?
2. 지금 상태를 즉시 알아야 하는가?
3. 실행 결과를 되돌리기 어렵거나 충돌 해결처럼 긴급한가?
4. 현재 문서의 맥락을 유지한 채 실행해야 하는가?

이 기준에 따라 정상 저장 상태와 경로는 숨긴다. 충돌과 연결 오류만 지속해서 표시한다. 내용 복사·사본 만들기·Finder에서 보기·링크 복사는 메뉴에 둔다.

### 구현 단위

현재 `App.tsx`에 분리되어 있는 작은 저장 상태 행과 `TitleBar`의 역할을 다음처럼 재구성한다.

```text
DocumentScrollArea
├── DocumentLead
│   ├── SidebarToggle (collapsed only)
│   ├── EditableDocumentTitle
│   ├── PropertiesTrigger
│   └── DocumentActionsMenu
├── FrontmatterPanel (expanded only for detailed editing)
└── DocumentBody

DocumentAlertLayer
└── ConflictOrConnectionBanner
```

`DocumentHeader`는 표시와 상호작용을 담당하고 저장·이름 변경·라우팅의 실제 상태는 기존 store가 소유한다. `FrontmatterPanel`은 별도의 상태 복제 없이 현재 탭의 frontmatter를 직접 사용해야 한다.

첫 구현 범위는 다음으로 제한한다.

1. 현재 저장 상태 전용 행을 제거한다.
2. `TitleBar`를 스크롤 영역의 첫 요소로 유지하고 속성·문서 메뉴를 합친다.
3. 저장 상태는 Open Tabs 항목의 점으로만 표시하고 저장 완료 시 제거한다.
4. 열린 탭 우클릭 메뉴에 `폴더에서 보기`와 경로 관련 작업을 추가한다.
5. 기존 내용 복사를 문서 메뉴로 옮긴다.
6. `FrontmatterPanel`을 속성 버튼에서 여는 popover와 상세 인라인 편집에 연결한다.

완료 조건은 다음과 같다.

- 사용자가 열린 탭 우클릭의 `폴더에서 보기`로 현재 파일의 위치를 찾는다.
- 링크 복사와 내용 복사의 차이가 메뉴 이름만으로 이해된다.
- 속성 패널에서 `status`를 바꾸면 폴더 보드에 같은 값이 반영된다.
- 정상 상태에서는 긴 문서를 스크롤할 때 고정 문서 헤더가 남지 않는다.
- 반쪽 창에서도 제목, 오류 상태, 문서 메뉴를 사용할 수 있다.

## 6. 핵심 개선안

### 6.1 문서와 폴더에 안정적인 URL을 부여한다

예시 URL 체계는 다음과 같다.

```text
/w/:workspaceKey/home
/w/:workspaceKey/note/:encodedPath
/w/:workspaceKey/folder/:encodedPath?view=list
/w/:workspaceKey/folder/:encodedPath?view=board
/w/:workspaceKey/search?q=keyword
```

정확한 형태보다 아래 동작을 보장하는 것이 중요하다.

- 직접 주소로 문서 또는 폴더 화면을 열 수 있다.
- 문서 이동 시 URL과 `document.title`이 함께 갱신된다.
- 뒤로/앞으로 이동 시 문서, 검색어, 폴더 보기, 필터, 스크롤 위치가 복원된다.
- 내부 링크는 실제 `<a href>` 의미를 유지해 Cmd/Ctrl+클릭과 가운데 클릭을 지원한다.
- 새로고침 후 워크스페이스를 다시 등록하고 같은 상대 경로를 연다.
- 존재하지 않거나 이동된 파일은 복구 가능한 오류 화면을 제공한다.

현재 서버의 `wsId`는 프로세스 생명주기 안에서만 유효하다. URL에는 이 값을 영구 식별자로 그대로 사용하지 않는 편이 좋다. 서버 재시작 후에도 사용자가 승인한 로컬 폴더를 다시 연결할 수 있는 `workspaceKey` 또는 안전한 별칭이 필요하다.

localhost 링크를 복사할 때는 “이 컴퓨터의 Maek에서 열리는 링크”라는 성격을 안내해야 한다. 외부 공유 링크와 혼동되면 안 된다.

### 6.2 브라우저 방문 기록에 작업 맥락을 포함한다

문서 ID만 기록해서는 충분하지 않다. 방문 기록 상태에는 화면 복원에 필요한 최소 맥락을 포함한다.

```ts
type MaekHistoryState = {
  workspaceKey: string;
  route: "home" | "note" | "folder" | "search";
  path?: string;
  folderView?: "list" | "board";
  query?: string;
  filters?: Record<string, string[]>;
  scrollTop?: number;
};
```

스크롤 이벤트마다 방문 기록을 쓰기보다 화면을 떠날 때 현재 상태를 `replaceState`로 저장하고, 의미 있는 화면 전환에만 `pushState`를 사용하는 방식이 적합하다.

대표 완료 시나리오는 다음과 같다.

> 폴더 보드에서 카드를 열고 상태와 본문을 수정한 뒤 브라우저 뒤로 가기를 누르면, 이전 보드의 필터와 스크롤 위치로 돌아온다.

### 6.3 폴더를 목록·보드가 공존하는 하나의 화면으로 만든다

우클릭으로 여는 별도 칸반보다 폴더 화면 상단에 `목록 | 보드` 전환을 제공한다.

목록 보기에는 다음을 제공한다.

- 제목
- 주요 상태
- 수정 시각
- 폴더 경로 또는 하위 폴더
- 선택 및 일괄 작업 진입점

보드 보기에는 다음을 제공한다.

- 상태별 레인
- 카드 수
- 드래그 또는 메뉴를 통한 상태 변경
- 새 문서 생성
- 필터와 정렬
- 문서를 열었다 돌아왔을 때의 위치 복원

현재 칸반은 선택한 폴더의 직접 자식 Markdown 파일만 읽는다. 초기 UI에서 이 범위를 명시해야 한다. 이후 필요하면 “하위 폴더 포함”을 옵션으로 추가한다.

### 6.4 문서 속성을 편집 흐름에 연결한다

이미 구현된 frontmatter 속성 UI를 문서 제목 아래에 연결한다.

- 접힌 상태에서는 `status`, 날짜, 태그 등 핵심 속성만 요약한다.
- 펼친 상태에서는 속성형 편집 UI를 제공한다.
- YAML이 잘못된 경우 원문 모드로 전환하고 오류 위치를 설명한다.
- 칸반 카드 이동과 문서 속성 변경이 같은 저장 규칙과 충돌 처리 규칙을 사용한다.
- 문서에서 상태를 바꾸고 보드로 돌아오면 즉시 반영된다.

이 연결은 신규 데이터 모델 없이도 기존 기능의 활용도를 크게 높인다.

### 6.5 홈을 작업 재개 화면으로 바꾼다

홈의 우선순위는 통계보다 작업 재개다.

권장 구성은 다음과 같다.

- 마지막 편집 문서와 저장 상태
- 최근 문서
- 최근 작업한 폴더
- 고정한 문서
- 빠른 새 노트
- 워크스페이스 변경

열린 탭 수나 테마 같은 정보는 사용자 행동으로 이어지지 않으므로 축소하거나 설정으로 이동한다.

### 6.6 검색을 두 단계로 구분한다

빠른 파일 열기는 현재 기능을 유지한다. 본문 검색은 별도 검색 화면으로 확장한다.

빠른 파일 열기:

- 파일명과 경로 검색
- 최근 문서 우선
- 키보드 중심 선택
- 빠른 화면 전환

본문 검색:

- 일치한 문장과 강조 표시
- 폴더 경로
- 파일 유형과 속성 필터
- 결과 정렬
- 문서를 열고 돌아왔을 때 검색어와 결과 위치 복원
- 새 탭 열기 지원

본문 검색은 서버 인덱싱 또는 파일 스캔 전략이 필요한 신규 기능이므로 정보 구조 개선과 분리해 계획한다.

### 6.7 고급 편집 기능의 발견성을 높인다

슬래시 메뉴와 선택 툴바는 숙련자에게 빠르지만 처음 사용하는 사람에게 보이지 않는다.

문서 상단 또는 빈 문단에 작은 `삽입` 진입점을 제공하고 다음 기능을 노출한다.

- 이미지
- 표
- 코드 블록
- 수식
- 체크리스트
- 내부 노트 링크

기존 슬래시 명령은 그대로 유지한다. 화면의 진입점은 학습을 돕고 슬래시 메뉴는 속도를 담당한다.

### 6.8 읽기와 비교 작업을 지원한다

읽기 모드는 링크 이동, 텍스트 선택, 인쇄에 집중한다. 편집 모드는 작성 도구와 속성을 제공한다.

PDF, HTML, 이미지 자료를 보며 노트를 쓰는 사용이 확인된다면 “옆에서 열기”를 추가한다. 기본 화면에 항상 두 패널을 두기보다 문서 메뉴나 드래그를 통한 선택 기능으로 제공한다.

## 7. 브라우저 기본 동작과의 공존

### 7.1 링크

가능한 모든 문서·폴더·검색 결과 항목은 링크의 의미를 가져야 한다.

- 일반 클릭: 같은 탭에서 연다.
- Cmd/Ctrl+클릭: 새 브라우저 탭에서 연다.
- 가운데 클릭: 새 브라우저 탭에서 연다.
- 링크 주소 복사: 같은 로컬 Maek에서 다시 열 수 있는 주소를 복사한다.

편집 중인 문서 본문에서는 단순 클릭이 커서 배치를 방해할 수 있으므로 현재와 같은 명시적 링크 열기 규칙을 유지하되, modifier 키와 컨텍스트 메뉴 동작을 보강한다.

### 7.2 단축키

브라우저 기본 단축키를 덮는 조합은 보조 경로로만 취급한다. 모든 주요 기능은 화면에서도 실행할 수 있어야 한다.

검토가 필요한 충돌 조합:

- `Cmd/Ctrl+P`: 브라우저 인쇄와 파일 검색
- `Cmd/Ctrl+O`: 브라우저 파일 열기와 파일 검색
- `Cmd/Ctrl+N`: 새 창과 새 노트
- `Cmd/Ctrl+W`: 브라우저 탭 닫기와 내부 문서 닫기

유지 가능성이 높은 조합:

- 편집 영역 안의 `Cmd/Ctrl+S`: 현재 문서 저장
- 앱 전용 조합 또는 명령 팔레트에서 실행되는 기능

대상 브라우저마다 실제 선점 동작을 검증해 단축키 도움말을 확정한다.

### 7.3 여러 탭과 충돌

같은 파일을 여러 브라우저 탭에서 편집할 수 있으므로 기존 외부 변경 감지 위에 명확한 설명을 추가한다.

- “다른 Maek 탭 또는 외부 앱에서 변경됨”을 구분 가능한 범위에서 표시한다.
- 다시 불러오기, 사본 저장, 닫기를 한곳에 제공한다.
- 가능하면 로컬 변경과 디스크 버전의 차이를 확인할 수 있게 한다.
- 탭 간 저장 충돌과 세션 식별자의 독립성을 테스트한다.

현재 브라우저 세션 ID는 `sessionStorage` 기반이다. 새 창을 여는 방식에 따라 opener의 저장소가 초기 복사될 수 있으므로, 서로 다른 탭을 동일 세션으로 오인하는지 검증해야 한다.

## 8. 반응형 레이아웃

모바일 제품으로 확장하는 것보다 먼저 Mac의 반쪽 창, 작은 노트북 화면, 브라우저 확대 상태를 지원한다.

권장 구간:

- 넓은 창: 고정 사이드바 + 중앙 문서 + 선택형 보조 패널
- 중간 창: 축소 가능한 사이드바 + 중앙 문서
- 좁은 창: 오버레이 서랍형 사이드바 + 단일 문서 화면

구체적인 원칙:

- 파일 검색창과 모달은 `min()` 및 화면 여백 기준으로 폭을 계산한다.
- 제목·경로·저장 상태가 겹치면 경로를 축약하고 작업 메뉴로 이동한다.
- 편집 본문은 기본 720–800px 범위의 읽기 폭을 검토한다.
- 표, 코드, 보드에는 넓은 보기 또는 가로 스크롤을 제공한다.
- 터치 입력에서도 기본 작업이 가능하도록 작은 아이콘 버튼의 클릭 영역을 확보한다.
- 사이드바 상태와 문서 스크롤은 화면 크기가 달라져도 안전하게 복원한다.

## 9. 시각 디자인 방향

### 9.1 시각적 명제

> 따뜻한 문서 공간. 탐색은 조밀하고 명료하며, 본문은 오래 읽고 쓰기 편하다.

현재의 따뜻한 중성색과 벽돌색 강조는 Maek의 개성으로 유지할 가치가 있다. 다만 넓은 상시 패널의 유리 효과와 그림자는 줄이고, 메뉴·팝오버·임시 도구처럼 실제로 떠 있는 요소에 깊이 표현을 집중한다.

### 9.2 색상

현재 체계를 출발점으로 사용한다.

- 배경: `#F8F7F2`
- 문서 표면: `#FFFFFF`
- 본문: `#171717`
- 보조 텍스트: `#6B7280`
- 강조: `#C04E3E`

강조색은 현재 선택, 링크, 주요 작업에 제한해서 사용한다. 성공·경고·오류는 별도의 의미 색을 사용하고 색상만으로 상태를 전달하지 않는다.

### 9.3 타이포그래피

초기 후보는 다음과 같다.

- 한글 UI와 본문: Pretendard
- 영문 UI 또는 보조 후보: Source Sans 3
- 코드: JetBrains Mono

Maek는 로컬에서 동작하므로 외부 CDN 의존보다 폰트를 함께 제공하는 방식을 우선 검토한다. 최종 글꼴은 실제 한국어 장문, 코드 블록, 표가 함께 있는 문서로 비교해야 한다.

### 9.4 간격과 밀도

- 기본 간격 단위: 4px
- 탐색 행: 조밀한 밀도
- 본문과 설정: 편안한 밀도
- 모서리: 작은 요소 4–6px, 패널 8–12px
- 모든 요소에 같은 큰 radius를 사용하지 않는다.

### 9.5 움직임

움직임은 상태 이해를 돕는 범위로 제한한다.

- hover와 focus: 80–120ms
- 패널 열기와 화면 전환: 150–220ms
- 저장 완료, 충돌, 드롭 위치는 짧고 명확한 상태 변화 사용
- `prefers-reduced-motion`을 존중

## 10. 접근성 기준

웹 네이티브 개선은 접근성 개선과 함께 진행한다.

- 모든 주요 작업을 키보드로 수행할 수 있어야 한다.
- `focus-visible`을 제거하지 않고 현재 위치가 명확한 포커스 표시를 제공한다.
- 트리, 탭, 목록, 메뉴의 ARIA 역할과 키보드 규칙을 각각 맞춘다.
- 아이콘 버튼에는 이해 가능한 이름과 툴팁을 제공한다.
- 저장·오류·충돌 상태는 라이브 영역과 텍스트로 전달한다.
- 색상 대비를 라이트·다크 테마 모두에서 검사한다.
- 브라우저 확대 200%에서 주요 기능을 사용할 수 있어야 한다.

## 11. 단계별 실행 계획

### Phase 1. 주소 기반 탐색

범위:

- URL 스키마 정의
- 문서·폴더·홈·검색 라우팅
- 뒤로/앞으로 및 새로고침 복원
- `document.title`
- 링크 복사와 새 탭 열기
- 서버 재시작 후 워크스페이스 재연결

완료 조건:

- 특정 문서 URL을 새 탭에 붙여 넣어 열 수 있다.
- 문서 간 이동 후 뒤로/앞으로가 기대대로 동작한다.
- 새로고침 후 같은 문서와 스크롤 근처로 돌아온다.
- 이동되거나 삭제된 문서는 복구 가능한 오류 상태를 보인다.

### Phase 2. 폴더 보기와 속성 연결

범위:

- 폴더 화면 추가
- 목록·보드 전환
- 문서 속성 패널 연결
- 상태 변경 동기화
- 폴더 보기와 스크롤 복원

완료 조건:

- 사용자가 우클릭 없이 폴더의 보드 보기를 발견할 수 있다.
- 문서에서 상태를 바꾸면 보드에 반영된다.
- 보드에서 문서를 편집한 뒤 뒤로 가면 같은 보드 위치로 돌아온다.

### Phase 3. 탐색과 홈 재구성

범위:

- 사이드바 정보 구조 변경
- 홈을 작업 재개 중심으로 변경
- 최근 폴더와 즐겨찾기
- 열린 문서 영역 축소 및 역할 명확화

완료 조건:

- 경로를 기억하지 않아도 최근 작업을 재개할 수 있다.
- 열린 문서가 많아도 폴더 탐색 공간이 유지된다.
- 주요 기능이 우클릭에만 의존하지 않는다.

### Phase 4. 반응형·키보드·접근성

범위:

- 중간·좁은 창 레이아웃
- 모달 크기 조정
- 브라우저 단축키 충돌 정리
- 포커스·ARIA·상태 알림 개선
- 본문 읽기 폭 설정

완료 조건:

- Mac 반쪽 창과 200% 확대에서 문서를 탐색하고 편집할 수 있다.
- 키보드만으로 폴더 탐색, 문서 열기, 편집, 저장이 가능하다.
- 브라우저 기본 동작을 예기치 않게 막지 않는다.

### Phase 5. 검색과 비교 작업 확장

범위:

- 본문 검색
- 속성·폴더 필터
- 검색 결과의 URL 및 복원
- 선택형 나란히 보기

완료 조건:

- 여러 검색 결과를 확인해도 검색어와 위치가 유지된다.
- PDF 또는 다른 문서를 참고하며 노트를 편집할 수 있다.

## 12. 우선순위 표

| 순서 | 개선 묶음 | 기대 효과 | 비용·위험 |
|---|---|---|---|
| 1 | 문서 URL, 방문 기록, 새 탭 | 브라우저 사용 모델의 기반 확립 | 워크스페이스 식별과 복원 설계 필요 |
| 2 | 속성 패널, 폴더 목록·보드 | 기존 기능 활용도 상승 | 저장·충돌 상태 동기화 필요 |
| 3 | 사이드바와 홈 | 기능 발견과 작업 재개 개선 | 내부 탭 역할에 대한 사용 검증 필요 |
| 4 | 반응형·키보드·접근성 | 다양한 창과 입력 방식 지원 | 브라우저별 검증 필요 |
| 5 | 본문 검색·필터·나란히 보기 | 조사와 비교 작업 강화 | 인덱싱과 성능 설계가 필요 |

## 13. 대표 사용자 시나리오

가장 먼저 구현하고 검증할 흐름은 다음과 같다.

1. 사용자가 사이드바에서 프로젝트 폴더를 연다.
2. 폴더 화면에서 보드 보기를 선택한다.
3. `Doing` 카드 하나를 새 브라우저 탭 또는 같은 탭에서 연다.
4. 문서의 `status`와 본문을 수정한다.
5. 자동 저장 결과를 확인한다.
6. 같은 탭이었다면 브라우저 뒤로 가기를 누른다.
7. 이전 보드의 필터와 스크롤 위치가 복원된다.
8. 수정된 카드가 올바른 레인에 표시된다.

이 시나리오는 주소 기반 탐색, 기능 발견, Markdown 속성, 저장, 충돌, 화면 복원을 한 번에 검증한다.

## 14. 측정 지표

개선 효과는 다음 지표로 확인할 수 있다.

- 최근 작업 문서를 다시 여는 데 걸리는 시간과 클릭 수
- 폴더에서 보드 보기를 처음 발견하는 비율
- 검색 결과를 확인한 뒤 검색을 다시 입력하는 횟수
- 뒤로 가기 후 기대한 화면으로 복귀한 비율
- 새 탭으로 문서를 비교하는 작업의 성공률
- 좁은 창과 200% 확대에서 핵심 작업 완료율
- 속성 변경 후 보드와 문서 사이의 상태 불일치 발생률
- 여러 브라우저 탭 편집 시 충돌 손실 건수

## 15. 검증이 필요한 가정과 위험

- 사용자가 내부 열린 문서 목록과 브라우저 탭을 어떤 식으로 나누어 쓰는지 관찰이 필요하다.
- `wsId`를 영구 URL에 사용할 수 없으므로 안정적인 워크스페이스 별칭 설계가 필요하다.
- localhost 링크는 다른 기기나 서버가 꺼진 상태에서는 열리지 않는다.
- 브라우저별 단축키 선점 동작은 실제 환경에서 확인해야 한다.
- `sessionStorage` 기반 세션 ID가 새 탭과 새 창에서 충분히 독립적인지 확인해야 한다.
- 현재 속성 UI를 편집 화면에 연결할 때 기존 자동 저장과 중복 상태가 생기지 않는지 확인해야 한다.
- 본문 검색은 큰 워크스페이스에서 성능과 파일 변경 동기화 전략이 필요하다.
- 모바일 지원이 실제 목표인지, 데스크톱 크기의 브라우저만 지원할지 제품 범위를 확정해야 한다.

## 17. 권장 첫 구현 단위

첫 구현 단위는 “문서 URL 전체 도입”보다 범위를 작게 잡되 이후 구조를 버리지 않도록 구성한다.

1. 홈, 문서, 폴더 보드에 최소 라우트를 부여한다.
2. 문서 전환과 `popstate`를 연결한다.
3. 문서 제목과 브라우저 탭 제목을 동기화한다.
4. 칸반 진입점을 폴더 헤더의 보기 전환으로 노출한다.
5. 문서 속성 패널을 실제 편집 화면에 연결한다.
6. 대표 사용자 시나리오를 E2E 테스트로 고정한다.

이 단위를 끝내면 Maek은 데스크톱 앱을 브라우저에 표시하는 단계에서 벗어나, 브라우저의 탐색 기능을 제품 기능으로 사용하는 워크스페이스가 된다.
