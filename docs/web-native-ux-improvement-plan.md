# Maek 웹 네이티브 UI/UX 개선 분석과 태스크 청크

## 문서 목적

Maek 웹 버전은 macOS 앱의 기능을 브라우저로 옮긴 제품이다. 실제 폴더와 Markdown 파일을 그대로 편집하고 자동 저장, 외부 변경 감지, 칸반, 미리보기까지 제공하지만, 탐색과 화면 구성은 아직 데스크톱 앱의 창 모델에 가깝다.

이 문서는 분석과 실행 계획을 분리하지 않는다. 각 태스크 청크 안에서 다음 질문을 함께 답한다.

- 지금 무엇이 문제인가?
- 왜 브라우저에서는 다르게 설계해야 하는가?
- 사용자는 무엇이 달라졌다고 느끼는가?
- 어디까지 구현하며 무엇은 제외하는가?
- 어떤 증거가 있어야 완료인가?

태스크 번호는 구현 순서와 의존성을 나타낸다. 세부 작업은 `TC-01.1`처럼 표기하며 이슈나 PR로 나누더라도 번호는 유지한다.

## 공통 제품 원칙

> Maek 웹은 데스크톱 앱을 브라우저 안에 복제한 화면이 아니라, 로컬 폴더를 탐색하고 문서를 읽고 쓰며 같은 자료를 목록·보드·미리보기로 다루는 웹 워크스페이스다.

모든 청크는 다음 원칙을 공유한다.

- 브라우저 주소, 방문 기록, 링크, 새 탭을 제품 기능으로 사용한다.
- 폴더 트리는 로컬 파일 기반 제품의 중심 탐색으로 유지한다.
- Maek 내부 탭은 같은 맥락 안의 빠른 전환과 미저장 상태 확인에 사용한다.
- 브라우저 탭은 독립 작업, 비교, 다른 작업 맥락 유지에 사용한다.
- 브라우저 탭 바가 이미 세로 공간을 차지하므로 고정 헤더와 중복 크롬을 최소화한다.
- 정상 상태는 조용하게 표현하고 충돌과 연결 오류처럼 조치가 필요한 상태만 지속해서 표시한다.
- 새 데이터 모델을 만들기 전에 이미 구현된 탐색기, frontmatter, 칸반, 미리보기를 연결한다.

## TC-01. 영속적인 워크스페이스 URL 기반

**상태:** 다음

### 분석 이유

현재 서버의 `wsId`는 실행 중인 프로세스 안에서만 유효하다. 이 값을 URL에 직접 넣으면 서버 재시작 후 주소가 무효가 되고, 사용자는 같은 폴더를 다시 선택해야 한다. 반대로 로컬 절대 경로를 URL에 넣으면 사용자 이름과 폴더 구조가 방문 기록, 스크린샷, 로그에 노출된다.

문서 URL, 방문 기록, 새 탭 기능을 구현하려면 먼저 서버 수명과 분리된 안전한 워크스페이스 식별자가 필요하다.

### 디자인 결정

- URL에는 로컬 절대 경로와 임시 `wsId`를 사용하지 않는다.
- 사용자가 승인한 폴더를 가리키는 안정적인 `workspaceKey`를 사용한다.
- 키로 폴더를 찾지 못하면 빈 화면 대신 재연결 흐름을 제공한다.
- localhost 링크는 외부 공유 링크가 아니라 현재 컴퓨터의 Maek 링크임을 명시한다.

### 사용자 흐름

1. 사용자가 워크스페이스를 처음 연다.
2. Maek이 안전한 별칭을 만들고 `/w/:workspaceKey/home`으로 이동한다.
3. 사용자가 새로고침하거나 같은 주소를 새 탭에 붙여 넣는다.
4. 서버가 폴더를 다시 등록하고 같은 홈을 연다.
5. 폴더가 이동되었거나 권한이 사라졌다면 재선택 안내를 보여준다.

### 구현 범위

- `TC-01.1` `workspaceKey` 생성, 저장, 중복 처리 규칙
- `TC-01.2` `/w/:workspaceKey/home` 진입 경로
- `TC-01.3` 서버 재시작 후 폴더 재등록
- `TC-01.4` 이동·삭제·권한 해제 상태의 복구 UI
- `TC-01.5` URL, 로그, 오류 메시지의 경로 노출 검사

### 완료 조건

- 홈 URL을 새로고침해 같은 워크스페이스로 돌아온다.
- 서버 재시작 후 같은 URL을 열어도 사용자가 승인한 폴더를 복원한다.
- 복원이 불가능하면 사용자가 원인을 이해하고 폴더를 다시 연결할 수 있다.
- URL에 로컬 절대 경로가 노출되지 않는다.

### 위험과 검증

- 키를 아는 것만으로 승인하지 않은 폴더에 접근할 수 없어야 한다.
- 폴더 이동과 이름 변경을 동일 워크스페이스로 볼지 제품 규칙이 필요하다.
- 여러 브라우저 프로필에서 승인 상태가 어떻게 다른지 확인한다.

### 관련 구현

- `client/src/host.ts`
- `client/src/store.ts`
- `server/workspaces.ts`
- `server/host.ts`

## TC-02. 문서·폴더 직접 주소와 브라우저 제목

**상태:** 대기 · **선행:** `TC-01`

### 분석 이유

현재 문서 열기와 전환은 `openFile`, `setActiveTab` 같은 내부 상태로만 처리된다. 사용자는 특정 문서 주소를 복사하거나 새 브라우저 탭에서 바로 열 수 없고, 새로고침 결과도 내부 세션 복원 규칙에 의존한다.

웹에서 화면은 주소와 대응해야 한다. 그래야 링크, 방문 기록, 새 탭이라는 브라우저 기능을 다음 청크에서 사용할 수 있다.

### 디자인 결정

```text
/w/:workspaceKey/home
/w/:workspaceKey/note/:encodedPath
/w/:workspaceKey/folder/:encodedPath?view=list
/w/:workspaceKey/folder/:encodedPath?view=board
```

정확한 문자열보다 문서와 폴더의 상대 경로를 손실 없이 인코딩하고, 직접 진입과 내부 이동이 같은 화면을 만드는 것이 중요하다.

### 구현 범위

- `TC-02.1` 상대 경로 인코딩·디코딩 규칙
- `TC-02.2` 홈·문서·폴더 라우트
- `TC-02.3` 내부 상태와 URL의 단일 동기화 지점
- `TC-02.4` 문서명·워크스페이스명과 `document.title` 동기화
- `TC-02.5` 삭제·이동·지원하지 않는 파일의 오류 화면

### 완료 조건

- 특정 문서 URL을 새 브라우저 탭에 붙여 넣어 열 수 있다.
- 같은 URL을 새로고침해 동일 문서로 돌아온다.
- 문서를 바꾸면 URL과 브라우저 탭 제목이 함께 바뀐다.
- 이동되거나 삭제된 파일에서 홈, 검색, 다시 연결 중 하나를 선택할 수 있다.

### 위험과 검증

- 한글, 공백, `#`, `%`, 깊은 경로를 포함한 파일명을 테스트한다.
- URL 상태와 기존 `.maek/tabs.json` 복원 중 어느 쪽이 우선하는지 명시한다. 직접 URL 진입에서는 URL이 우선이다.
- 잘못된 인코딩이 워크스페이스 밖의 경로 접근으로 이어지지 않아야 한다.

### 관련 구현

- `client/src/App.tsx`
- `client/src/store.ts`
- `client/src/host.ts`
- `server/workspaces.ts`

## TC-03. 브라우저 방문 기록과 작업 맥락 복원

**상태:** 대기 · **선행:** `TC-02`

### 분석 이유

주소만 바뀌고 방문 기록에 작업 맥락이 없으면 뒤로 가기는 문서만 바꿀 뿐 이전 보드의 필터와 스크롤 위치를 잃는다. 특히 검색 결과나 보드에서 여러 문서를 확인할 때 사용자는 매번 원래 조건을 다시 만들어야 한다.

### 디자인 결정

의미 있는 화면 전환에만 `pushState`를 사용한다. 스크롤 이벤트마다 기록을 추가하지 않고, 화면을 떠날 때 현재 상태를 `replaceState`로 저장한다.

```ts
type MaekHistoryState = {
  workspaceKey: string;
  route: "home" | "note" | "folder" | "search";
  path?: string;
  folderView?: "list" | "board";
  query?: string;
  filters?: Record<string, string[]>;
  scrollTop?: number;
};
```

### 사용자 흐름

1. 사용자가 폴더 보드에서 필터를 적용하고 아래로 스크롤한다.
2. 카드 하나를 같은 탭에서 연다.
3. 문서를 수정하고 자동 저장을 기다린다.
4. 브라우저 뒤로 가기를 누른다.
5. 이전 보드의 보기, 필터, 스크롤 위치가 복원된다.

### 구현 범위

- `TC-03.1` 화면 전환의 `pushState` 규칙
- `TC-03.2` 현재 화면 상태의 `replaceState` 규칙
- `TC-03.3` `popstate`와 store 전환 연결
- `TC-03.4` 폴더 보기·필터·검색어·스크롤 복원
- `TC-03.5` 새로고침과 기존 세션 상태의 우선순위

### 완료 조건

- 문서 간 이동 후 뒤로·앞으로가 예상한 문서를 연다.
- 보드와 검색에서 문서를 확인한 뒤 원래 맥락으로 돌아온다.
- 뒤로 가기가 중복 기록 때문에 같은 화면에 머물지 않는다.
- 저장 중 뒤로 가도 변경이 손실되지 않는다.

### 위험과 검증

- 자동 저장과 `popstate`가 동시에 발생하는 경쟁 상태를 테스트한다.
- 파일이 이동된 방문 기록은 복구 화면으로 연결한다.
- 스크롤 위치는 콘텐츠 변경 후 유효 범위로 보정한다.

### 관련 구현

- `client/src/App.tsx`
- `client/src/store.ts`
- `client/src/features/database/kanban/FolderKanbanView.tsx`
- `client/src/features/editor/components/FilePicker.tsx`

## TC-04. 브라우저 링크와 새 탭 동작

**상태:** 대기 · **선행:** `TC-02`, 전체 복원은 `TC-03`

### 분석 이유

클릭 가능한 요소가 내부 이벤트만 실행하면 브라우저는 그것을 링크로 인식하지 못한다. Cmd/Ctrl+클릭, 가운데 클릭, 링크 주소 복사, 새 탭 열기가 사라지고 사용자는 Maek 내부 탭만 사용해야 한다.

### 디자인 결정

- 문서, 폴더, 검색 결과는 가능한 범위에서 실제 `<a href>` 의미를 갖는다.
- 일반 클릭은 같은 브라우저 탭, modifier 클릭과 가운데 클릭은 새 브라우저 탭에서 연다.
- 편집기 본문 링크는 커서 배치와 충돌하므로 현재의 명시적 열기 규칙을 유지하되 modifier와 메뉴 동작을 보강한다.
- `문서 링크 복사`, `Markdown 내용 복사`, `상대 경로 복사`를 이름과 결과로 구분한다.

### 구현 범위

- `TC-04.1` 탐색기·검색 결과·내부 링크의 `href`
- `TC-04.2` Cmd/Ctrl+클릭과 가운데 클릭
- `TC-04.3` 열린 탭과 문서 메뉴의 복사 작업
- `TC-04.4` 로컬 전용 링크 토스트
- `TC-04.5` 여러 브라우저 탭의 세션 ID와 저장 충돌 검증

### 완료 조건

- 링크를 새 브라우저 탭에서 열 수 있다.
- 브라우저의 링크 주소 복사가 다시 열 수 있는 Maek URL을 만든다.
- 복사 메뉴 이름만 보고 링크, 파일 내용, 파일 경로의 차이를 이해할 수 있다.
- 같은 파일을 두 탭에서 수정하면 조용히 덮어쓰지 않고 충돌을 알린다.

### 위험과 검증

- `sessionStorage`가 새 탭 생성 방식에 따라 복사되는지 브라우저별로 검사한다.
- localhost 링크가 다른 기기에서 열리지 않는다는 점을 공유 링크처럼 오해하지 않게 한다.
- 편집 중 링크 클릭이 텍스트 선택과 커서 이동을 방해하지 않아야 한다.

### 관련 구현

- `client/src/features/explorer/Explorer.tsx`
- `client/src/features/editor/MarkdownEditor.tsx`
- `client/src/features/editor/components/TitleBar.tsx`
- `client/src/host.ts`

## TC-05. 고정 헤더 없는 문서 리드와 속성 패널

**상태:** 다음

### 분석 이유

브라우저 탭 바 때문에 줄어든 콘텐츠 높이를 회복하려고 고정 문서 헤더를 제거했다. 여기에서 다시 제목, breadcrumb, 저장 문구, 속성 행을 여러 층으로 쌓으면 같은 문제가 반복된다. 반면 현재 존재하는 `FrontmatterPanel`과 `PropertiesView`가 기본 편집 흐름에 연결되지 않으면 칸반이 사용하는 `status`를 문서에서 직접 수정하기 어렵다.

### 디자인 결정

- 제목은 고정 헤더가 아니라 문서 스크롤 영역의 첫 요소다.
- 제목 오른쪽에는 `속성`과 `•••`만 둔다.
- 속성은 기본적으로 본문을 밀지 않는 popover로 연다.

## TC-07. 문서 속성과 보드 상태 동기화

**상태:** 대기 · **선행:** `TC-05`, `TC-06`; 전체 시나리오는 `TC-03`

### 분석 이유

문서의 `status`와 보드 카드의 레인은 같은 frontmatter를 표현한다. 두 화면이 서로 다른 임시 상태나 저장 코드를 사용하면 한쪽의 변경이 다른 쪽에 늦게 반영되거나 외부 변경과 충돌하면서 손실될 수 있다.

### 디자인 결정

- 문서 속성과 카드 이동은 같은 파일 저장·hash·mtime 충돌 규칙을 사용한다.
- 화면별로 별도 진실 공급원을 만들지 않고 디스크와 열린 탭 상태를 일관되게 갱신한다.
- 충돌 시 어느 화면에서 시작했는지와 무관하게 같은 해결 UI를 사용한다.

### 사용자 흐름

1. 사용자가 보드의 `Doing` 카드를 연다.
2. 문서 속성에서 `status`를 `Done`으로 변경한다.
3. 저장 후 뒤로 가기로 보드에 돌아온다.
4. 같은 카드가 `Done` 레인에 표시되고 이전 필터와 스크롤이 유지된다.

### 구현 범위

- `TC-07.1` 문서 속성 변경 후 보드 데이터 갱신
- `TC-07.2` 카드 이동 후 열린 문서와 frontmatter 갱신
- `TC-07.3` 외부 변경과 동시 저장 충돌 처리
- `TC-07.4` 저장 실패 시 optimistic UI 되돌리기
- `TC-07.5` 대표 흐름 E2E 테스트

### 완료 조건

- 문서와 보드 어느 쪽에서 상태를 바꿔도 다른 화면에 즉시 반영된다.
- 저장 실패나 외부 변경에서 카드와 문서가 서로 다른 상태로 남지 않는다.
- 브라우저 뒤로 가기로 같은 보드 맥락에 복귀한다.

### 위험과 검증

- 같은 문서를 여러 브라우저 탭에서 편집하는 경우를 포함한다.
- 드래그 중 파일 변경, 문서 rename, 카드 삭제를 테스트한다.
- 상태 값이 보드 레인에 없을 때의 fallback 규칙을 명시한다.

## TC-09. 반응형 레이아웃과 브라우저 단축키

**상태:** 대기 · **선행:** `TC-05`, `TC-06`, `TC-08`의 주요 레이아웃

### 분석 이유

웹은 전체 화면 데스크톱 창만 사용하지 않는다. Mac 반쪽 창, 작은 노트북, 브라우저 확대에서 고정 폭 모달과 상시 사이드바는 본문을 압박한다. `Cmd/Ctrl+P`, `O`, `N`, `W`는 브라우저의 인쇄, 파일 열기, 새 창, 탭 닫기와 충돌한다.

### 디자인 결정

- 넓은 창: 고정 사이드바, 중앙 문서, 선택형 보조 패널

- 좁은 창: 오버레이 서랍형 사이드바와 단일 문서
- 본문은 기본 720~800px 읽기 폭을 검토한다.
- 표, 코드, 보드는 필요한 경우 가로 스크롤이나 넓은 보기를 제공한다.
- 브라우저가 선점하는 단축키는 보조 경로로만 취급하고 모든 주요 기능에 화면 진입점을 둔다.

### 구현 범위

- `TC-09.1` 실제 콘텐츠 기준 breakpoint 확정
- `TC-09.2` 오버레이 사이드바와 포커스 관리
- `TC-09.3` 검색창·모달의 `min()` 기반 폭
- `TC-09.4` 본문 읽기 폭과 넓은 콘텐츠 처리
- `TC-09.5` 충돌 단축키 제거·변경·도움말 반영
- `TC-09.6` 터치 입력의 클릭 영역

### 완료 조건

- Mac 반쪽 창에서 폴더 탐색, 문서 편집, 속성, 오류 해결을 수행한다.
- 좁은 창에서 제목과 문서 메뉴가 겹치지 않는다.
- 브라우저의 인쇄·새 탭·탭 닫기를 예상치 못하게 막지 않는다.
- 모달이 화면 밖으로 벗어나지 않는다.

### 위험과 검증

- Safari, Chrome, Firefox의 단축키 선점 차이를 실제로 확인한다.
- 화면 크기가 바뀌어도 사이드바 상태와 문서 스크롤을 안전하게 복원한다.

## TC-10. 키보드·ARIA·확대 접근성

**상태:** 대기 · **선행:** `TC-09`

### 분석 이유

트리, 탭, 메뉴는 모양만 비슷한 목록이 아니라 서로 다른 키보드 규칙을 가진다. 저장 점이나 색상만으로 상태를 전달하면 스크린 리더와 색각 사용자는 의미를 알 수 없다. 200% 확대는 단순 시각 테스트가 아니라 실제 레이아웃의 정보 손실을 드러낸다.

### 디자인 결정

- 트리, 탭, 목록, 메뉴에 각각 맞는 역할과 키보드 이동을 적용한다.
- `focus-visible`을 유지하고 popover·모달 종료 후 합리적인 위치로 포커스를 돌린다.
- 저장, 충돌, 연결 오류는 색상과 함께 이름 또는 텍스트를 제공한다.
- 움직임은 `prefers-reduced-motion`을 존중한다.

### 구현 범위

- `TC-10.1` 폴더 트리·Open Tabs·메뉴의 키보드 규칙
- `TC-10.2` 포커스 표시, trap, 복귀
- `TC-10.3` 상태의 accessible name과 live region
- `TC-10.4` 아이콘 버튼 이름과 툴팁
- `TC-10.5` 라이트·다크 대비
- `TC-10.6` 200% 확대와 reduced motion

### 완료 조건

- 키보드만으로 폴더 탐색, 문서 열기, 속성 수정, 저장을 완료한다.
- 포커스가 사라지거나 화면 밖 요소에 갇히지 않는다.
- 색상을 보지 않아도 저장 중, 충돌, 연결 오류를 구분한다.
- 200% 확대에서 핵심 작업과 오류 메시지가 가려지지 않는다.

### 위험과 검증

- react-arborist와 Radix의 기본 키보드 동작을 중복 구현하지 않는다.
- 자동 저장 알림이 지나치게 자주 읽히지 않도록 상태 변화 빈도를 조절한다.
- 자동 검사 외에 실제 키보드 이동과 스크린 리더 흐름을 수동 검증한다.

## TC-11. 본문 검색과 자료 비교

**상태:** 대기 · **선행:** `TC-02`~`TC-04`; 나란히 보기는 `TC-09`

### 분석 이유

현재 검색은 파일명과 경로로 문서를 빠르게 여는 기능이다. 이는 명령 팔레트로는 유용하지만 본문에서 정보를 찾고 여러 결과를 비교하는 검색과는 다르다. 검색이 독립 화면이 아니면 사용자는 문서를 확인할 때마다 검색어를 다시 입력해야 한다.

PDF, HTML, 이미지 미리보기도 이미 존재하지만 참고 자료와 노트를 함께 보는 흐름으로 연결되어 있지 않다.

### 디자인 결정

- 빠른 파일 열기와 본문 검색을 서로 다른 작업으로 유지한다.
- 본문 검색은 URL, 필터, 결과 위치를 갖는 독립 화면으로 만든다.
- 검색 결과는 실제 링크로 제공해 새 브라우저 탭에서 열 수 있다.
- 나란히 보기는 기본 레이아웃이 아니라 사용자가 요청할 때만 연다.

### 구현 범위

- `TC-11.1` 큰 워크스페이스를 고려한 인덱싱 또는 파일 스캔 전략
- `TC-11.2` 일치 문장과 강조 표시
- `TC-11.3` 폴더·파일 유형·속성 필터와 정렬
- `TC-11.4` 검색 URL과 결과 스크롤 복원
- `TC-11.5` 새 탭 열기와 링크 복사
- `TC-11.6` PDF·HTML·이미지와 문서의 선택형 나란히 보기

### 완료 조건

- 여러 결과를 열어도 검색어, 필터, 결과 위치가 유지된다.
- 파일명 검색과 본문 검색의 차이를 진입점과 화면에서 이해할 수 있다.
- 외부 파일 변경 후 검색 결과가 오래된 상태로 남지 않는다.
- 참고 자료를 보면서 노트를 편집할 수 있고, 원하면 단일 화면으로 돌아간다.

### 위험과 검증

- 큰 워크스페이스에서 시작 시간, 메모리, 변경 반영 지연을 측정한다.
- 바이너리·숨김·`.maek` 파일이 검색 대상에 들어가지 않게 한다.
- HTML 아티팩트의 격리와 파일 접근 규칙을 유지한다.

### 측정 지표

- 검색 결과 확인 후 같은 검색어를 다시 입력한 횟수
- 첫 결과가 나타나는 시간과 변경 파일 반영 지연
- 여러 자료를 비교하는 작업의 완료율

## 실행 순서와 병렬화

주 경로는 다음과 같다.

```text
TC-01 → TC-02 → TC-03 → TC-04
                  │
TC-05 ─────┐      │
           ├→ TC-07 → TC-08 → TC-09 → TC-10
TC-06 ─────┘

TC-02 + TC-03 + TC-04 + TC-09 → TC-11
```

- `TC-01`과 `TC-02`는 모든 웹 탐색 기능의 기반이므로 먼저 진행한다.
- `TC-05`와 `TC-06`은 각각 독립적으로 구현하고 `TC-07`에서 결합한다.
- `TC-03`이 끝나면 `TC-07`의 대표 뒤로 가기 시나리오를 완성할 수 있다.
- `TC-09`는 화면 구조가 정해지기 전에 시작하면 반복 수정이 커지므로 `TC-08` 이후 진행한다.
- `TC-11`의 검색 설계는 먼저 할 수 있지만 URL 복원과 나란히 보기 구현은 선행 청크가 필요하다.

## 첫 실행 묶음의 종료 조건

첫 실행 묶음은 `TC-01`부터 `TC-07`까지다. 다음 대표 시나리오가 하나의 E2E 테스트로 통과하면 종료한다.

1. 사용자가 주소로 워크스페이스의 폴더 화면을 연다.
2. 목록에서 보드 보기로 전환한다.
3. `Doing` 카드를 같은 탭 또는 새 브라우저 탭에서 연다.
4. 문서의 `status`와 본문을 수정한다.
5. Open Tabs의 저장 점이 사라질 때까지 기다린다.
6. 같은 탭이었다면 브라우저 뒤로 가기를 누른다.
7. 이전 보드의 필터와 스크롤 위치가 복원된다.
8. 수정한 카드가 올바른 레인에 표시된다.

이 시나리오는 주소 기반 탐색, 브라우저 링크, 방문 기록, frontmatter, 자동 저장, 보드 동기화를 한 번에 검증한다.

## 공통 시각 디자인 기준

각 태스크 청크에서 새 UI를 만들 때 다음 기준을 적용한다.

- 시각적 명제: 따뜻한 문서 공간. 탐색은 조밀하고 명료하며 본문은 오래 읽고 쓰기 편하다.
- 배경 `#F8F7F2`, 문서 표면 `#FFFFFF`, 본문 `#171717`, 보조 텍스트 `#6B7280`, 강조 `#C04E3E`를 현재 출발점으로 사용한다.
- 강조색은 현재 선택, 링크, 주요 작업에 제한한다.
- 성공·경고·오류는 별도 의미 색과 텍스트를 함께 사용한다.
- 기본 간격 단위는 4px로 두고 탐색 행은 조밀하게, 본문과 설정은 편안하게 구성한다.
- 모든 요소에 같은 큰 radius와 유리 효과를 적용하지 않는다. 깊이 표현은 메뉴·popover·모달처럼 실제로 떠 있는 요소에 집중한다.
- hover와 focus는 80~120ms, 패널과 화면 전환은 150~220ms 범위에서 검토한다.
- 한글 UI와 본문은 Pretendard, 코드는 JetBrains Mono를 우선 후보로 두되 외부 CDN보다 로컬 제공을 검토한다.

## 공통 성공 지표

- 최근 작업 문서를 다시 여는 시간과 클릭 수
- 폴더 보드를 처음 발견하는 비율
- 뒤로 가기 후 기대한 화면으로 복귀하는 비율
- 새 브라우저 탭으로 문서를 비교하는 작업의 성공률
- 좁은 창과 200% 확대에서 핵심 작업 완료율
- 속성 변경 후 보드와 문서 사이의 불일치 발생률
- 여러 브라우저 탭 편집에서 변경 손실이 발생한 건수

이 지표는 전체 프로젝트가 끝난 뒤 한 번 측정하지 않는다. 각 청크의 완료 조건과 연결해 해당 사용자 흐름이 바뀌는 시점에 측정한다.
